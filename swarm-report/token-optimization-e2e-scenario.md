### Реальная экономия от кеша

- Кеш активировался в Validating: сэкономлено **$0.061** (cache_read: 22,763 tokens)
- Без кеша задача стоила бы: **$0.479**
- С кешем: **$0.418**
- **Экономия от prompt caching: 12.7%**

### Почему кеш НЕ работает в Executing

**Причина: system + tools ≈ 962 tokens < 1024 (минимум Anthropic)**

Доказательство:
- Executing turn 1: `input=1289` (всё как обычные input tokens, cache=0)
- Validating turn 1: `input=327, cache_creation=1339` (system+tools = 1339 > 1024)

Validating prompt длиннее т.к. включает **execution results** (5 шагов с описаниями), что добавляет ~400 tokens и переводит через порог 1024.

### Почему общая стоимость выросла

1. **Executing: 16 turns vs 13** — агент создал README, запустил дополнительные проверки
2. **Validating: 18 turns vs 7** — первая попытка достигла max turns (10) без вызова submit_validation, потребовалась вторая попытка

Основная проблема — НЕ в кешировании, а в **избыточности агентов**. Кеш экономит ~13% на input tokens, но лишние turns дороже.

## Рекомендации

### Быстрые фиксы (высокий ROI)
1. **Увеличить executing system prompt** до >1024 tokens — добавить контекст задачи, примеры — чтобы кеш активировался
2. **Снизить max turns для Validating** с 10 до 7 — предотвращает "переанализ"
3. **Добавить инструкцию "вызови submit_validation сразу после проверки"** в validating prompt

### Средний приоритет
4. **Frontend: отображать cache поля** в usage stats (chat.ts строки 173-180 не трекают cache_creation/cache_read)
5. **Tool result truncation** — не дал эффекта на этой задаче (вывод bubble sort < 4000 chars), но полезен для задач с большими файлами

### Для оценки
6. **Тест с длинным system prompt** (>2048 tokens) — покажет реальный потенциал кеша на ~30%+ экономии
